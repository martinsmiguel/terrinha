1. Visão Geral e Definição de Produto

1.1 Resumo Executivo

Crônicas da Vila é um jogo de estratégia em tempo real (RTS) simplificado, que roda inteiramente no navegador, é jogável offline e suporta partidas multiplayer locais entre 2 e 4 jogadores conectados à mesma rede Wi-Fi. O jogo combina a mecânica central de Age of Empires II (coleta de recursos, construção, treino de unidades e combate) com a estética leve, colorida e social de jogos de navegador clássicos como Club Penguin.

O projeto é 100% open source, sem dependência de serviços proprietários ou bibliotecas com licenças restritivas. Sua arquitetura é modular baseada em plugins: cada sistema do jogo (movimento, coleta, combate, rede, renderização) é um plugin independente que se comunica via eventos, com interface explícita e ciclo de vida próprio. Essa escolha permite que os sistemas sejam desenvolvidos, testados e substituídos de forma isolada, sem que um quebre o outro.

1.3 Objetivos e Não-Objetivos

Objetivos

  • Oferecer uma experiência RTS acessível, com curva de aprendizado de menos de 5 minutos.
  • Priorizar a interação social (chat, cores de civilização, lobby amigável) em vez do realismo histórico.
  • Garantir funcionamento totalmente offline, com multiplayer apenas na rede local.
  • Manter toda a stack sob licenças open source permissivas.
  • Adotar arquitetura modular em que cada sistema do jogo é um plugin substituível.

Não-Objetivos

  • Não ser um simulador histórico ou realista.
  • Não ter campanha single-player extensa.
  • Não ter gráficos 3D de alta fidelidade.
  • Não suportar partidas via internet pública (apenas rede local).
  • Não ter monetização, microtransações ou cadastro de usuário.
  • Não adotar frameworks pesados de injeção de dependência (ex: Cordis completo).

4. Arquitetura de Software (Plugin Host)

4.1 Visão Geral

A arquitetura é organizada em quatro pilares: Plugin Host (kernel mínimo), Event Bus (comunicação), Plugins de Domínio (sistemas do jogo) e Camada de Rede P2P via WebRTC. Cada plugin declara o que oferece, o que consome e quais eventos emite/escuta. O kernel apenas resolve dependências, roteia eventos e gerencia o ciclo de vida. Nenhuma lógica de jogo vive no kernel.

4.5 Modelo de Sincronização (Lockstep Determinístico)

  1. Cada jogador executa a simulação localmente em ticks fixos (20 ticks/s).
  2. Comandos (mover, construir, atacar) são enviados para todos os pares com um tick alvo.
  3. Nenhum comando é aplicado antes de todos os pares confirmarem recebimento daquele tick.
  4. A simulação é determinística: mesma sequência de comandos = mesmo estado final.
  5. Checksum periódico detecta divergência; cliente divergente é ressincronizado.

5. Sistema de Plugins (GamePlugin)

O sistema de plugins é o coração da arquitetura. Ele é deliberadamente simples: uma interface TypeScript, um EventEmitter e um registro de serviços. Nada mais. O kernel não conhece nenhum sistema de jogo específico.

5.1 Interface GamePlugin

// src/core/plugin.ts
export interface PluginContext {
  events: EventBus;
  services: ServiceRegistry;
  logger: Logger;
  config: Record<string, unknown>;
}

export interface GamePlugin {
  /** Nome único do plugin (usado como namespace de serviços). */
  name: string;

  /** Plugins dos quais este depende (init só roda após eles). */
  dependencies?: string[];

  /** Eventos que este plugin emite. */
  emits?: string[];

  /** Eventos que este plugin escuta. */
  listens?: string[];

  /** Chamado uma vez quando o plugin é registrado e dependências prontas. */
  init(ctx: PluginContext): void | Promise<void>;

  /** Chamado quando o plugin é desregistrado (para limpeza de recursos). */
  destroy?(): void | Promise<void>;
}

5.2 Event Bus (Implementação Mínima)

// src/core/event-bus.ts
export type EventHandler = (payload: unknown) => void;

export class EventBus {
  private handlers = new Map<string, Set<EventHandler>>();

  on(event: string, handler: EventHandler): () => void {
    if (!this.handlers.has(event)) this.handlers.set(event, new Set());
    this.handlers.get(event)!.add(handler);
    return () => this.off(event, handler);
  }

  off(event: string, handler: EventHandler): void {
    this.handlers.get(event)?.delete(handler);
  }

  emit(event: string, payload: unknown): void {
    this.handlers.get(event)?.forEach(h => h(payload));
  }
}

5.3 Plugin Host (Kernel)

// src/core/host.ts
export class PluginHost {
  private plugins = new Map<string, GamePlugin>();
  private initialized = new Set<string>();
  private events = new EventBus();
  private services = new ServiceRegistry();

  register(plugin: GamePlugin): void {
    if (this.plugins.has(plugin.name)) {
      throw new Error(`Plugin "${plugin.name}" já registrado`);
    }
    this.plugins.set(plugin.name, plugin);
  }

  async init(): Promise<void> {
    const order = this.resolveDependencies();
    for (const name of order) {
      const plugin = this.plugins.get(name)!;
      await plugin.init({
        events: this.events,
        services: this.services,
        logger: createLogger(name),
        config: {},
      });
      this.initialized.add(name);
    }
  }

  private resolveDependencies(): string[] {
    const order: string[] = [];
    const visited = new Set<string>();

    const visit = (name: string) => {
      if (visited.has(name)) return;
      const plugin = this.plugins.get(name);
      if (!plugin) throw new Error(`Plugin "${name}" não encontrado`);
      visited.add(name);
      plugin.dependencies?.forEach(visit);
      order.push(name);
    };

    this.plugins.forEach((_, name) => visit(name));
    return order;
  }

  async destroy(): Promise<void> {
    for (const name of [...this.initialized].reverse()) {
      await this.plugins.get(name)?.destroy?.();
    }
    this.initialized.clear();
  }
}

5.4 Exemplo de Plugin: Coleta

// src/plugins/gathering/index.ts
export const gatheringPlugin: GamePlugin = {
  name: 'gathering',
  dependencies: ['movement', 'ecs'],

  emits: ['resource:gathered', 'animation:play'],
  listens: ['command:gather'],

  init({ events, services }) {
    const ecs = services.get('ecs');
    const movement = services.get('movement');

    events.on('command:gather', (payload) => {
      const { unitId, targetId } = payload as GatherCommand;

      movement.send(unitId, getPosition(targetId));

      const arrivalHandler = () => {
        setTimeout(() => {
          const amount = 10;
          ecs.mutate(unitId, 'inventory', inv => inv.wood += amount);
          events.emit('resource:gathered', { unitId, resource: 'wood', amount });
          events.emit('animation:play', { unitId, clip: 'chop' });
        }, 2000);
      };

      events.on(`unit:arrived:${unitId}`, arrivalHandler);
    });
  },
};

Breaking changes:
  Adicionar "!" após o tipo ou rodapé "BREAKING CHANGE:" → MAJOR

Exemplos:

git commit -m "feat(gathering): adiciona plugin de coleta de madeira [#12]"
git commit -m "plugin(render-canvas2d): adiciona alternativa ao Three.js [#24]"
git commit -m "fix(pathfinding): corrige A* travando em grid isométrico [#15]"
git commit -m "feat(network)!: muda formato de comando para JSON [#22]

BREAKING CHANGE: comandos agora usam JSON em vez de string."

Template de ADR:

# ADR-0005: Por que não usar Cordis como framework de plugins

## Status
Aceito — 2026-XX-XX

## Contexto
Consideramos adotar o Cordis (usado no DeepSeek Harness) como framework de injeção
de dependência e ciclo de vida de plugins.

## Decisão
Implementar um Plugin Host próprio com menos de 300 linhas de TypeScript,
usando um EventBus simples em vez do modelo de serviços do Cordis.

## Consequências
- Pro: Kernel mais simples, mais fácil de entender e depurar.
- Pro: Sem dependência pesada; menor superfície de ataque.
- Pro: Curva de aprendizado menor para contribuidores.
- Contra: Sem hot-reload automático (mitigado pelo HMR do Vite).
- Contra: Sem injeção de dependência automática (resolvida por ordem topológica).

name: Sincronizar board com PR

  pull_request:
    types: [opened, ready_for_review, closed]

  update-board:
    runs-on: ubuntu-latest
    steps:
      - name: Mover para In Review
        if: github.event.action == 'opened' || github.event.action == 'ready_for_review'
        uses: actions/github-script@v7
        with:
          github-token: ${{ secrets.ADD_TO_PROJECT_PAT }}
          script: |
            const body = context.payload.pull_request.body || '';
            const matches = body.match(/#(\d+)/g) || [];
            for (const m of matches) {
              const issueNumber = parseInt(m.replace('#', ''), 10);
              console.log(`Movendo issue #${issueNumber} para In Review`);
            }

      - name: Mover para Done
        if: github.event.action == 'closed' && github.event.pull_request.merged
        uses: actions/github-script@v7
        with:
          github-token: ${{ secrets.ADD_TO_PROJECT_PAT }}
          script: |
            console.log('PR mergeado — mover cards para Done');

12.3 Workflow C — Bump de Versão SemVer

.github/workflows/version-bump.yml

name: Bump de versão SemVer

on:
  push:
    branches: [main]

jobs:
  bump:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Instalar sley
        run: |
          curl -L https://github.com/dominikbraun/sley/releases/latest/download/sley-linux-amd64 -o sley
          chmod +x sley

      - name: Determinar bump
        id: bump
        run: |
          COMMITS=$(git log --format=%B -n 20)
          if echo "$COMMITS" | grep -qE "BREAKING CHANGE|!:"; then
            echo "type=major" >> $GITHUB_OUTPUT
          elif echo "$COMMITS" | grep -qE "^feat|^plugin"; then
            echo "type=minor" >> $GITHUB_OUTPUT
          else
            echo "type=patch" >> $GITHUB_OUTPUT
          fi

      - name: Aplicar bump
        run: ./sley bump ${{ steps.bump.outputs.type }}

      - name: Commit e push
        run: |
          git config user.name "github-actions"
          git config user.email "actions@github.com"
          git add .version CHANGELOG.md
          git commit -m "chore(release): v$(cat .version)"
          git push

ITEM_ID=$(gh api graphql -f query='
  query($issue: Int!) {
    repository(owner: "SEU_USUARIO", name: "SEU_REPO") {
      issue(number: $issue) {
        projectItems(first: 1) { nodes { id } }
      }
    }
  }' -F issue=$ISSUE --jq '.data.repository.issue.projectItems.nodes[0].id')

gh api graphql -f query='
  mutation($project: ID!, $item: ID!, $field: ID!, $value: String!) {
    updateProjectV2ItemFieldValue(input: {
      projectId: $project
      itemId: $item
      fieldId: $field
      value: { singleSelectOptionId: $value }
    }) { projectV2Item { id } }
  }' -F project=$PROJECT_ID -F item=$ITEM_ID -F field=$FIELD_ID -F value=${STATUS[$COLUNA]}

echo "Issue #$ISSUE movida para '$COLUNA'"

15.1 Padrões Adotados do DeepSeek Harness

O DeepSeek Harness foi analisado como referência arquitetural. Nem tudo foi adotado; a tabela abaixo registra o que foi incorporado, adaptado ou descartado, com justificativa.

Padrão do HarnessDecisãoComo/Justificativa
Everything-is-a-plugin Adotado (em escala reduzida) Plugin Host mínimo + interface GamePlugin. Cada sistema do jogo é um plugin.
Vendorização de dependências Adotado peerjs, three, ws em vendor/.
ADRs no repositório Adotado docs/explanation/adr/ integrado ao Diátaxis.
Snapshot testing Adotado vitest.snapshot.config.ts para verificar determinismo.
Múltiplas configs de teste Adotado 6 arquivos vitest.*.config.ts para diferentes camadas.
Cordis completo Descartado Overkill; Kernel próprio com ~150 linhas cobre o caso.
Monorepo pnpm Descartado Repositório único com pastas bem organizadas é suficiente.
Multi-linguagem (Python, Rust) Descartado Tudo TypeScript/JavaScript no navegador.
Múltiplas apps (Web + Desktop) Descartado Apenas Web (navegador) como alvo.
Desenvolvimento via IA (AGENTS.md) Adotado parcialmente Uso de OpenCode + Ollama; AGENTS.md como guia para assistentes.
